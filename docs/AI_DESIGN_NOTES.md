# 배틀 AI 설계 노트

프로젝트 소유자가 정리한 요구 사항과, 구현 전에 정해야 할 것들을 기록합니다. (작성: 2026-10, 계속 갱신)
**"요구"는 소유자가 말한 내용이고, "메모"는 구현 방향에 대한 제안입니다.** 확정되지 않은 것은 `[미정]`으로 표시했습니다.

---

## 1. 요구 사항 (소유자 설명 그대로 정리)

### 1-1. 만들 AI 두 종류
| | 설명 | 우선순위 |
|---|---|---|
| **A. 메타데이터 기반 AI** | 사이트(pokemondb, OP.GG 등)에서 가져온 메타 정보(사용률, 채용 세트 등)를 바탕으로 만든 AI | **먼저 만든다** |
| **B. 생(生) 데이터 딥러닝 AI** | 메타 정보 없이 규칙과 데이터만으로 딥러닝(자기 대전 등)으로 학습한 AI | 여유가 있을 때 |

### 1-2. AI가 내야 하는 결과
- 모든 **선택지마다 승률(%)** 을 계산한다.
- 선택지의 종류: **첫 파티 선출**(6마리 중 3마리), **기술 선택**, **교체할 포켓몬** 등.

### 1-3. 가상 배틀 GUI (AI 데이터가 쌓인 뒤)
- 내 파티와 상대 파티(6마리)를 입력한다.
- **턴마다 결과를 입력**하면, 어떤 행동이 최선의 수인지 계산해 주는 **시뮬레이션**.

### 1-4. 숨겨진 정보 추론 (중요)
- 상대의 **기술·도구·특성은 모른다.** 알 수 있는 것은 상대 파티 6마리, 상대의 선출, 그리고 **턴을 진행하며 공개된 정보**뿐이다.
- 공개된 정보로 상대의 **도구와 기술을 유추**해야 한다.
- 공개된 정보가 늘어날수록 승률도 달라져야 한다.
- 이 추론은 **메타데이터에 따라 바뀔 수 있게** 만든다. (메타가 바뀌면 추론도 바뀐다)

### 1-5. 메타 수집
- 출처: pokemondb, OP.GG 등.
- **티어(래더 점수대)별로 나누어** 수집할 수 있으면 좋다.
  - 중간 티어: 평범한 세트가 많다.
  - 저티어/고티어: 창의적인 기술 채용이 많을 것이다 → 티어마다 분포가 다르게 쓰이도록.

### 1-6. 최종 목표 (선택 사항)
- 포켓몬 게임 화면을 **이미지 검색**하거나 **게임 프로그램을 감지**해서, 각 선택지의 승률을 **화면에 오버레이**로 보여 주는 프로그램 (HSReplay 같은 형태).

### 1-7. 데이터베이스
- 포켓몬·기술·특성 등의 **일본어 이름**을 DB에 추가한다. → **완료** (`name_ja`, 폼은 `form_name_ja`). 게임 화면 인식(1-6)에도 쓸 수 있다.

## 2. 메모: "딥러닝으로 만들어지는 건가?"에 대한 정리

소유자가 AI 쪽은 잘 몰라서 질문한 부분입니다. 결론부터: **전부 딥러닝일 필요는 없고, 메타 AI(A)의 핵심은 "확률 추론 + 시뮬레이션"입니다.** 딥러닝은 속도와 정확도를 높이는 부품으로 쓰입니다.

| 해야 할 일 | 보통 쓰는 방법 | 딥러닝 필요? |
|---|---|---|
| 데미지/효과 계산 | 규칙 엔진 (DB + `ai/damage_calc.py`, 또는 Showdown) | 아니오 |
| 상대의 숨은 세트 추정 (도구/기술/특성) | 메타 사용률을 "사전 확률"로 쓰고, 공개된 정보로 **베이즈 갱신** | 아니오 (통계) |
| 선택지별 승률 | 추정한 상대 세트 여러 개를 뽑아 **수백~수천 번 가상 배틀(몬테카를로)** 해서 비율 계산 | 아니오 |
| 탐색 속도 향상, 평가 | 학습된 **가치망/정책망**으로 앞을 덜 보고도 판단 | 예 (선택) |
| 메타 없이 처음부터 학습 (B) | **자기 대전 강화학습** | 예 (B의 핵심) |

따라서 A는 "메타 통계 + 베이즈 추론 + 시뮬레이션 탐색"으로 먼저 만들고, 이후 B에서 딥러닝을 본격 도입해 A의 가치망을 대체/보강할 수 있습니다.

### 승률 계산의 두 가지 어려움 `[미정: 접근 방식]`
1. **정보가 숨겨져 있다** → 상대 세트를 확률분포로 들고 다니며(1-4), 분포에서 뽑아 시뮬레이션한 결과를 평균한다.
2. **양쪽이 동시에 행동한다** → "내가 이 기술을 쓰면 상대가 뭘 쓸지"에 따라 결과가 달라진다. 단순 평균이 아니라 상대의 행동 분포(메타 기반 또는 최선 대응 가정)를 가정해 기대 승률을 구한다. (게임이론의 혼합 전략/내시 균형 근사)

## 3. 메모: 구조 제안

```
[메타 수집]  pokemondb / OP.GG / ...  --(티어별)-->  meta_* 테이블 (날짜·레귤레이션·티어 버전)
                                              |
[규칙 엔진]  DB + ai/damage_calc.py (+ Showdown으로 검증)   <---- 이미 구축/검증 중
                                              |
[추론기]     상대 세트 분포 = 메타 사전확률 x 공개 정보 갱신 (도구/기술/특성/SP)
                                              |
[탐색기]     샘플된 세트로 가상 배틀 롤아웃 -> 선택지별 승률%  (선출 / 기술 / 교체)
                                              |
[인터페이스] 가상 배틀 GUI (1-3)  ->  (선택) 화면 인식 오버레이 (1-6)
```

- **티어별 메타(1-5)**: 추론기의 사전확률을 `tier` 파라미터로 바꿔 끼울 수 있게 설계한다. (예: 저티어 분포 / 중티어 / 고티어)
- **메타가 바뀌면**: 사전확률만 교체하면 추론과 승률이 함께 바뀐다. (1-4 요구) → 메타는 날짜/레귤레이션/티어 버전으로 저장한다.
- **진행 상태(턴 정보)**: 지금 DB/계산기에서 빠져 있는 "전투 진행 상태"(이번 턴 먼저 맞았는지, 쓰러진 아군 수 등)를 GUI의 입력 형식과 함께 설계해야 한다. 같은 상태를 시뮬레이터에도 쓴다.

## 4. 단계별 계획 (제안)

1. ~~DB와 규칙 구조화, Showdown 대조 검증, 데미지 계산기~~ — 진행 완료(정적 데이터 차이 0건, 데미지 대조 일치율 99.99% 이상)
2. **메타 수집** (현재 우선): 출처 조사 → 수집 스크립트 → `meta_*` 스키마 (티어/날짜/레귤레이션 버전)
3. **상대 세트 추론기** + 승률 계산기 (A)
4. **턴 진행 상태 모델**과 전체 배틀 시뮬레이터(또는 Showdown 연결) → 선택지별 승률
5. **가상 배틀 GUI**
6. (여유 시) **B: 생 데이터 딥러닝 AI**
7. (선택) **화면 인식 오버레이**

## 5. 열린 질문 `[미정]`
- 메타 수집원별로 가져올 수 있는 지표와 **티어 구분 가능 여부** (조사 중)
- 사용 조건/이용 약관: 크롤링 허용 범위, 재배포 가능 여부
- 래더 티어 정의: 사이트마다 점수대 구분이 다름 → 공통 구간으로 매핑할지
- 동시 행동 문제의 처리 방식 (2절)
- 화면 오버레이는 게임 플랫폼(스위치 캡처/에뮬레이터/PC 등)에 따라 방식이 달라짐

### 판단 `[미정]`
- **티어별 분리(1-5)가 필요하면 Smogon 통계가 현재 유일하게 확인된 출처**다. 레이팅 구간 4개(0 / 1500 / 1630 / 1760)로 "저/중/고 티어" 분포를 만들 수 있다.
- **게임 내 실제 메타**는 OP.GG가 가까워 보이지만 레이팅 구분이 없다. 두 출처를 **각각 다른 `source` 로 저장**하고, 추론기에서 가중해서 쓰는 방식을 제안한다.
- 월 단위 스냅샷으로 `meta_*` 테이블에 쌓는다 (출처, 포맷, 레이팅 컷오프, 수집 월/일시 포함).

### 6-1. pokedb.tokyo (champs.pokedb.tokyo) — 소유자가 언급한 사이트
- 일본어 사이트이고, 확인한 것은 `robots.txt`뿐이다: **ClaudeBot, Claude-SearchBot, GPTBot, ChatGPT-User, PerplexityBot 등 AI 크롤러를 `Disallow: /` 로 전면 금지**한다. (처음 "pokedb"를 영어권 pokemondb.net으로 잘못 이해했었다.)
- 서버가 막는 것을 우회하지 않는다 → **자동 수집하지 않는다.** 이 사이트의 데이터가 필요하면 소유자가 직접 확인하거나 내보낸 파일을 제공하는 방식이 필요하다. `[미정]`

### 6-2. 수집 결과: Smogon 통계 (2026-10 수집, `etl/collect_meta_smogon.py`)
- 싱글 BSS **Reg M-A (2026-04~06) / M-B (06~09) / M-C (09)**, 레이팅 컷오프 **0 / 1500 / 1630 / 1760** → 스냅샷 32개, 약 122만 행.
- DB에 없는 포켓몬/도구/기술은 0개 (특성 `No Ability` 1개만 제외) → DB와 잘 맞물린다.
- **분석 메모 (M-C 2026-09, 상위 30마리 평균 기술 다양성)**: 컷오프 0 → 3.158, 1500 → 3.081, 1630 → 2.964, 1760 → 2.939 (엔트로피, 높을수록 다양).
  **레이팅이 높을수록 기술 구성이 오히려 비슷해진다**(상위 4개 기술이 차지하는 비중 72% → 76%). 소유자의 "고티어는 창의적" 가설과 반대 방향이다.
  단, (1) Showdown 래더 인구이고 (2) 컷오프 0은 모든 플레이어를 포함하며 (3) 상위권일수록 표본이 적어 불확실성이 크다. 게임 내 래더에서는 다를 수 있다 `[검증 필요]`.

### 6-3. "각 파티의 전투 상황" — 배틀 로그(리플레이) 수집 가능성
- **Showdown 공개 리플레이**: `replay.pokemonshowdown.com/search.json?format=gen9championsbssregmc` 로 최근 리플레이 목록(페이지당 51개, 일부는 레이팅 포함), `/{id}.json` 으로 전체 로그를 받을 수 있다. 챔피언스 싱글 M-C / M-B 모두 존재함을 확인했다.
- 로그에는 **양쪽 6마리 팀, 선출(teampreview 3), 턴별 교체·기술·데미지(HP %)·공개된 도구/특성·날씨·승패**가 있다.
- 이는 우리 AI가 실제로 보게 될 "공개 정보만 있는 관전 시점"과 같아서 **상대 세트 추론기 검증과 선출/교체 패턴 학습**에 바로 쓸 수 있다.
- 한계: 플레이어가 저장·공개한 리플레이만 있고(표본 편향), 안 쓴 기술/도구는 로그에 나오지 않으며, 레이팅이 없는 판이 많다. 게임 내 래더가 아니라 Showdown 인구다.
